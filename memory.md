- Mechanism: the action-observation loop (mod.rs ~4004-4068) has an asymmetry. `host_can_act` reads the host's `authoritative_state()` **in-process** (always fresh). `client_can_act` reads the client's `latest_snapshot`, which is **delivered over TCP** by a background receive thread (host id = constant `LOCAL_PLAYER_ID` "local-player"; client id = `format!("player-{instance_id}")`). When hand 1's first actor is the client, the only exit is via the network snapshot; under saturation the host tick/publish thread and/or the client receive thread are starved, so the snapshot reflecting the open action window can miss the test's 15s deadline → panic at mod.rs:4063 ("one live session should observe an open action window").
- Not a product concern (a real human waits ms for the snapshot). Fix options discussed but NOT yet applied: (a) drive the loop's "whose turn" decision off the host authoritative state and give the client-snapshot path a bounded active wait; (b) raise the 15s deadline; (c) reduce test parallelism for the heavy real-TCP tests. No code changed pending user decision.

- Storage: Local persistence for hand history
- Interop: Android compatibility layer

**Frontend (React 19 + TypeScript + Vite):**
- Rendering: Card display, hand history, tournament UI
- Screen flow: Lobby → Room → Table → Results
- User interaction: Betting, folding, raising
- Transient UI state only

**Multiplayer:**
- Host-authoritative state projection
- Raw TCP over LAN (no mock/simulator by default)
- Signed message verification
- Reconnect/resync protocol
- Session guards to prevent overlapping connections

**NPC/LLM:**
- Rule-based strategy (default, fast)
- LLM-enhanced reasoning (optional, timeout-based)
- Tilt mechanic for opponent tracking
- Never blocks hands on LLM failure
